# Конвенции

Сите endpoints на API-то ги следат **истите правила** — за формат на барања, формат на одговори, обработка на грешки, статус кодови и безбедност. Оваа страница ги собира тие заеднички конвенции на едно место, за да не се повторуваат на секоја поединечна API страница. Кога во документацијата за конкретен router пишува „одговорот е JSON" или „грешките се враќаат како `{"detail": ...}`", дефиницијата на тоа однесување е тука.

Целта е едноставна: кој било endpoint да се однесува предвидливо. Штом ќе ги научиш овие правила еднаш, ги знаеш за целиот backend.

## 1. Базен URL <a id="1-url"></a>

Сите патеки во документацијата се релативни на базниот URL. Во `main.py` се дефинирани **два** сервера:

| Околина | Базен URL |
|---------|-----------|
| Продукција (Render) | `https://klinicka-bolnica-stip2026.onrender.com` |
| Локален развој | `http://localhost:8000` |

Така, патека како `POST /pacienti/login` во продукција значи `https://klinicka-bolnica-stip2026.onrender.com/pacienti/login`.

> Frontend-от не го хардкодира URL-от — го **пресметува автоматски** според доменот на кој работи (види [Архитектура → Frontend слој](../../overview_na_sisitemot/architecture.md#3-frontend-sloj)).

## 2. Формат на барања <a id="2-baranja"></a>

Барањата што менуваат податоци (`POST`, `PATCH`, `DELETE`) праќаат **JSON** со заглавие `Content-Type: application/json`. Барањата за читање (`GET`) ги праќаат параметрите како **query параметри** во URL-от.

```http
POST /pacienti/login HTTP/1.1
Content-Type: application/json

{ "email": "ivan@example.com", "password": "Lozinka1." }
```

```http
GET /termini/dostapni?lekar_id=2&datum=2026-06-20 HTTP/1.1
```

| Тип на барање | Каде одат податоците | Пример |
|---------------|----------------------|--------|
| `GET` | Query параметри во URL | `?lekar_id=2&datum=2026-06-20` |
| `POST` / `PATCH` | JSON тело | `{ "email": "...", "password": "..." }` |
| `DELETE` | Query параметри (понекогаш JSON тело) | `?admin_doctor_id=1` |

> Дел од endpoints читаат `request.json()` директно наместо преку Pydantic модел. За тие е додаден `openapi_extra` на декораторот, за да Swagger/Scalar прикаже полиња за внес.

## 3. Формат на одговори <a id="3-odgovori"></a>

Сите успешни одговори се **JSON** со статус `200`. Резултатите се читаат од базата со `cursor(dictionary=True)`, па секој ред е објект со **именувани полиња** (не низа од вредности):

```json
[
  { "doctor_ID": 1, "name": "Ана", "surname": "Стојановска", "specijalnost": "Кардиологија" },
  { "doctor_ID": 2, "name": "Марко", "surname": "Петров", "specijalnost": "Неврологија" }
]
```

Дејствата што не враќаат податоци враќаат потврдна порака:

```json
{ "message": "Терминот е успешно закажан! Ќе добиете потврда на вашата е-пошта." }
```

> Имињата на полињата се на **латиница** (на пр. `ime`, `prezime`, `datum_pregled`), а вредностите можат да бидат на **кирилица** (имиња, дијагнози, специјалности). Базата користи `utf8mb4` за целосна поддршка на кирилица.

***

## 4. Формат на грешки <a id="4-greshki"></a>

Грешките се враќаат преку FastAPI `HTTPException`, што секогаш дава ист облик — објект со едно поле `detail`:

```json
{ "detail": "Овој термин е веќе закажан. Изберете друго време." }
```

Пораката во `detail` е наменета да биде **разбирлива за корисникот** и често се прикажува директно во интерфејсот. HTTP статус кодот го кажува типот на грешката (види подолу).

> **Исклучок:** endpoint-от `POST /ai-chat/ask` секогаш враќа `200` — дури и при грешка враќа учтива порака во полето `odgovor`, за да не се прекине разговорот со асистентот.

## 5. HTTP статус кодови <a id="5-statusi"></a>

| Код | Значење | Кога се враќа |
|-----|---------|---------------|
| `200` | OK | Успешно барање (читање или дејство) |
| `400` | Bad Request | Невалиден или недостасувачки влез (лош датум, празно поле, дупликат ЕМБГ, судир на термин кај апарат) |
| `401` | Unauthorized | Погрешна е-пошта/корисничко име или лозинка |
| `403` | Forbidden | Нема право на дејството (на пр. оценување туѓ преглед, пристап до admin без права) |
| `404` | Not Found | Ресурсот не постои (лекар, пациент, термин) |
| `409` | Conflict | Терминот е веќе зафатен при закажување преглед |
| `500` | Internal Server Error | Неочекувана грешка на серверот |

> Распределбата е намерна: `400` = „погрешен влез", `401/403` = „проблем со пристап/идентитет", `404` = „не постои", `409` = „судир при закажување". Поединечните API страници ги наведуваат конкретните кодови по endpoint.

## 6. Образец на endpoint <a id="6-obrazec"></a>

Скоро секој endpoint ја следи **истата сигурна шема**: отвори конекција, изврши SQL преку `dictionary=True` cursor, врати JSON, фати грешка со `HTTPException`, и **секогаш** затвори ја конекцијата во `finally`.

```python
# образец од backend/routers/lekari.py
@router.get("")
def get_lekari(specijalnost: Optional[str] = None):
    conn = None                                  # 1. нема конекција на почеток
    try:
        conn = get_connection()                  # 2. отвори конекција
        posrednik = conn.cursor(dictionary=True) # резултати како речници
        posrednik.execute(
            "SELECT doctor_ID, name, surname FROM Doctors WHERE specialty = %s",
            (specijalnost,)                       # параметри преку %s (не составување стринг!)
        )
        return posrednik.fetchall()              # 3. врати JSON
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))  # 4. форматирана грешка
    finally:
        if conn and conn.is_connected():         # 5. секогаш затвори конекција
            conn.close()
```

Зошто овој образец е важен:

* **`finally` блокот** гарантира дека конекцијата секогаш се затвора — без разлика дали барањето успеало или паднало. Така се спречува исцрпување на конекции кон базата.
* **`autocommit=False`** — измените (`INSERT`/`UPDATE`/`DELETE`) се потврдуваат експлицитно со `conn.commit()`; ако нешто падне, не остануваат полу-зачувани податоци.
* **`dictionary=True`** — одговорот е JSON со именувани полиња наместо анонимни низи.

## 7. Безбедност <a id="7-bezbednost"></a>

Неколку правила се применуваат **низ целиот backend**:

* **SQL параметри преку `%s`** — никогаш составување на SQL стринг со податоци од корисникот. Ова спречува **SQL injection**:

```python
# точно — параметрите одат одделно
cur.execute("SELECT * FROM patient WHERE email = %s", (email,))

# погрешно — никогаш вака
cur.execute(f"SELECT * FROM patient WHERE email = '{email}'")
```

* **Хеширани лозинки** — лозинките никогаш не се чуваат во чист текст; се хешираат со **bcrypt** (`password_utils.py`). Детали: [Автентикација → Лозинки](authentication.md#7-lozinki).
* **Тајни само од `.env`** — лозинки, клучеви и конекциски стрингови се читаат од `backend/.env`, никогаш не се хардкодирани во кодот.
* **Валидација на влез** — секој router ги проверува влезните податоци (формат на е-пошта, должина на ЕМБГ, валиден датум, без викенди) пред зачувување.

## 8. Транслитерација (кирилица ↔ латиница) <a id="8-translit"></a>

Дел од корисниците пишуваат на латиница, а податоците во базата се на кирилица. Затоа `routers/utils.py` нуди функција `transliterate_mk_to_lat()` што конвертира кирилица во латиница.

Се користи на две клучни места:

* при **најава на лекар** — корисничкото име е во формат `ime.prezime` на латиница, пресметано од кириличните име и презиме во базата;
* во **AI асистентот** — за да се препознае намерата без оглед на писмото на внесот.

> Поради различни начини на пишување (на пр. `sh`/`s`, `zh`/`z`, `ch`/`c`), најавата на лекар прифаќа и неколку толерантни варијации на корисничкото име. Види [Автентикација → Лекар](authentication.md#5-lekar).

## 9. Префикси на routers <a id="9-prefiksi"></a>

Секоја тема има свој router со свој **префикс**. Префиксите директно одговараат на nginx regex-от во продукција:

| Router | Префикс | API док. |
|--------|---------|----------|
| `lekari.py` | `/lekari` | [Лекари](lekari.md) |
| `pacienti.py` | `/pacienti` | [Пациенти](pacienti.md) |
| `termini.py` | `/termini` | [Термини](termini.md) |
| `admin.py` | `/admin` | [Администрација](admin.md) |
| `aparati.py` | `/aparati` | [Апарати](aparati.md) |
| `uslugi.py` | `/specialnosti`, `/uslugi` | [Услуги](uslugi.md) |
| `novosti.py` | `/novosti` | [Новости](novosti.md) |
| `kariera.py` | `/kariera`, `/aplikacija` | [Кариера](kariera.md) |
| `ai_chat.py` | `/ai-chat` | [AI чат](ai-chat.md) |

> Модулот `uslugi.py` е исклучок — неговите патеки (`/specialnosti`, `/uslugi`) се монтирани директно на коренот, без заеднички префикс.

## 10. CORS <a id="10-cors"></a>

Backend-от додава **CORS** middleware во `main.py`, што му дозволува на frontend-от (од друг домен или порта) да го повикува API-то од прелистувач:

```python
# backend/main.py
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],     # сите извори (за развој)
    allow_credentials=True,
    allow_methods=["*"],     # GET, POST, PATCH, DELETE...
    allow_headers=["*"],
)
```

> `allow_origins=["*"]` е практично за развој. Во построга продукција би се ограничило на конкретниот домен на порталот.

## 11. OpenAPI и тестирање <a id="11-openapi"></a>

FastAPI автоматски генерира **OpenAPI** спецификација од кодот. Достапна е на:

| URL | Намена |
|-----|--------|
| `/docs` | Swagger UI — интерактивно тестирање во прелистувач |
| `/redoc` | ReDoc — читлива документација |
| `/openapi.json` | Raw OpenAPI 3.0 (го користат GitBook и Scalar) |

Во документацијата, секоја API страница содржи вграден **OpenAPI блок** со копче **„Test it"** (Scalar), кое праќа барање директно кон живиот сервер — без да ја напушташ страницата. За да работи копчето, во `main.py` е дефинирано полето `servers` со продукциски и локален URL.

> По промена на backend: во GitBook → OpenAPI → **Check for updates**, па **Publish**, за да се освежи спецификацијата (`KlinickaBolnicaAPI`).
